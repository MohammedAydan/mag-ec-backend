# Threat Model

## Phase 09 Payment Threats

### Spoofed Provider Webhooks

- Threat: An attacker posts forged payment-success events directly to the webhook endpoint.
- Control: Stripe signature verification on the raw request body using `PAYMENT_WEBHOOK_SECRET`.

### Duplicate Or Replayed Webhooks

- Threat: Legitimate events are delivered multiple times and replay payment transitions.
- Control: `PaymentWebhookEvent` enforces uniqueness on `(provider, externalEventId)` and marks later deliveries as duplicates.

### Client-Side Payment Success Forgery

- Threat: A client claims a payment succeeded after receiving a client secret or SDK callback.
- Control: Order payment status becomes authoritative only after verified server-side webhook processing.

### Reservation Lock Abuse

- Threat: Customers place online-card orders that reserve stock indefinitely without paying.
- Control: Reservations remain time-bound and are released when payment failure or cancellation is verified.

### Secret Leakage

- Threat: Stripe secrets or webhook secrets leak through logs or config mishandling.
- Control: Secrets stay in environment configuration only, while request logging continues to redact sensitive headers and bodies.

## Residual Risks

- Orphaned provider payment intents are still possible if the provider object is created but the local transaction fails afterward.
- Refund execution is not live yet, so refund abuse controls are only partially implemented in phase 09.
- Live provider operational hardening, alerting, and replay tooling remain follow-up work for later phases.

## Phase 12 Release Threats

### Contract Drift

- Threat: The committed OpenAPI artifact differs from the API generated by the current source tree, causing Flutter clients to generate stale request or response models.
- Control: `pnpm openapi:verify` regenerates OpenAPI and fails when the checked-in artifact is not stable.

### Generated Client Breakage

- Threat: The OpenAPI document is syntactically valid but incompatible with the downstream Dart/Dio generator.
- Control: CI runs `pnpm flutter:client:verify` against the official OpenAPI Generator Docker image.

### Admin Surface Privilege Escalation

- Threat: Phase-11 admin support surfaces expose reports, audit logs, content writes, notifications, or review moderation to users with insufficient role or permission claims.
- Control: E2E coverage verifies missing-auth, wrong-role, and missing-write-permission denial paths for phase-11 admin controllers.

### Unbounded Report Export Abuse

- Threat: Attackers request unsupported or overly broad report exports to probe for sensitive data access.
- Control: Request DTO validation and service-level report type allowlists reject unsupported report types before export jobs are created.

### Operational Blind Spots

- Threat: Production incidents cannot be triaged quickly because expected signals, smoke checks, rollback steps, or incident records are not defined.
- Control: Release, monitoring, incident-response, and smoke-test runbooks define the minimum operational evidence required for release readiness.

### Dependency Advisory Drift

- Threat: Production dependencies gain known high or critical vulnerabilities after release.
- Control: `pnpm security:audit` runs the production dependency audit with a high-severity gate in CI.

## Phase 12 Known Advisory Snapshot

- No high or critical production advisory was reported in the local phase-12 audit run.
